# BD Shifts and Allocation: memory and joins review

Reviewed 5 November 2026 (Australia/Sydney). This is a source review, with no M edits, workbook reads, native execution or refresh actions.

The new core-to-Shifts enrichment prevents join fan-out. The main static memory concern is that it carries almost the entire core result through four-point, interval, endpoint and role expansions, with several buffers and sorts at the expanded width. The older Name-based legacy calculation can still multiply intermediate rows before its publication guard. These findings do not establish the cause of the currently running Core refresh: this review covers its downstream Shifts/Allocation consumers, not a measured Core execution profile.

## Memory and repeated evaluation

**High priority: wide enrichment happens before the multiplying stages.** Core currently publishes 73 columns. `CoreColumns` removes only four provenance columns, so `CoreResults = Table.Buffer(...)` holds 69 columns for the combined core result. The five-field join then expands 64 core attributes. `LocalUnit` is placed on the left rows, but the right core table is not filtered to that unit or its relevant shift keys before buffering (Shifts:523–555). Most core columns, including diagnostic text and repeated totals, are consequently copied through plotting and interval construction.

The wide buffers are visible at `StaffShifts` (Shifts:262), before and after interval expansion (186, 203, 219), and before/after endpoint construction (225, 239). Several sorts also run on those wide rows (187, 206, 208, 212, 218, 240). Buffering at 186 occurs before the start-only/null-boundary reductions at 196–197. A column/row reduction is only useful for materialisation if it precedes the relevant buffer; narrowing after it does not undo that allocation.

Shifts contains 13 `Table.Buffer` calls; Avg contains four. This count alone does not show a defect: the path-table buffers are small. The concern is the width and grain of the buffers above. Historical **metadata**, not a fresh saved-output inspection, records 83,152 `NAMES_INTERVALSLIST` rows in `before-inventory.json`. At that unchanged row count, 64 propagated core attributes represent about 5.3 million logical attribute values, before existing fields and intermediate copies. This is not a RAM-byte estimate or a current measured row count.

**The legacy branch becomes wide before it is narrowed.** `StaffDoubleShifts` starts from the enriched, buffered four-point `StaffShifts`. It joins on `Name, DateTime`, fills down globally in that order, then joins `Name` plus the filled start time to `DoubleShifts` (Shifts:387–396). `ShiftGapIndices` also groups by `Name` (313–326). Same-name/same-time rows can make these intermediate joins many-to-many. `LegacyShiftMeasures` selects its small working columns only afterward (575–579). Its guards reduce publication risk, but do not prevent earlier row growth or prove all same-code/multi-role Name/time assignments correct.

**Buffers are evaluation-local, not a workbook cache.** `RosterShiftsWithChecks` feeds plotting, boundary construction and legacy classification. Loaded `StaffDoubleShifts`, the new `OvertimeRosterChecks`, and `NAMES_INTERVALSLIST` can cause separate evaluations; their buffers do not guarantee one shared materialisation. Avg similarly reuses `ResourceIntervalAllocation` through multiple loaded aggregations and validation branches (Avg:160–270). The `IMPORT Shifts` buffer holds the navigation table whose `Data` cells are nested tables; it is not proof of one deep materialisation of every imported output (Avg:98–111). No read count, peak memory, concurrency or timing was measured here.

## Identity and consumer boundaries

`SourceShiftID` is the core's stable published-duty identity. `LocalShiftKey` includes the local input row number (Shifts:522–530): it distinguishes duplicate local rows and exists for unmatched planning rows, but must not be treated as a stable cross-refresh business ID. Core matching intentionally avoids `Name` and `NameRole`.

Both identifiers flow into `NAMES_INTERVALSLIST` and the ungrouped `ResourceIntervalAllocation`. They cease to be row identifiers in `ResourceShiftAllocation`, whose grouping keys are `ShiftDate, ShiftPeriod, IntervalAssociatedShift, Name, Role, TimeDate, Attribute` (Avg:162). That aggregate is not suitable for joining employee-level overtime back by Name/Role. The later role aggregation correctly counts only `StaffCount=1` and `Attribute="IntervalStart"` before summing (Avg:194–198).

No circular dependency was found in the reviewed enrichment chain: roster preparation → four points → legacy classification → plot/interval outputs → saved-table Allocation consumer. Reading the saved core table does not run the core workbook's query definitions.

## Proposed follow-up, not implemented

1. **First reduce materialised scope and width.** Filter the core side to the already fixed local unit before buffering; consider a distinct-key semi-join for exactly the local physical keys. Keep every key and required field. Prototype lean private legacy/aggregation branches and attach the full check attributes near final publication so the public schema and row grain remain unchanged. Do not silently remove requested Tableau attributes.
2. **Then address legacy intermediate fan-out.** Measure Name/time match multiplicities and private-row growth. A physical-identity repair to that legacy branch is separate business-rule work; its existing publication guards are not a substitute for preventing the expansion.
3. **Verify the remaining grid assumptions using the authorised saved-output checks.** Investigate actual duplicate `(IntervalID, Role)` or `(StartInterval, Role)` matches if observed. Avoid adding broad audit queries merely because these contracts are currently implicit.
4. **Narrow aggregation work and measure actual refresh behaviour.** In Avg, `ResourceShiftAllocation` filters `Attribute="IntervalStart"` after grouping by that same field (160–165); moving this proven-equivalent reduction before grouping is a candidate. Project only group keys and the two needed measures on private aggregation branches. Benchmark before/after with the approved workflow; retain existing publication checks and distinguish separate loaded-query evaluations from one evaluation's local buffering.

These are proposals requiring an authorised source change and the normal source/sync gates. Current source and runtime deployment remain unchanged by this review.
